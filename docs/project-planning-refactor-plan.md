## 0. 요약

- 현행 템플릿(doc-templates.md)은 2026-04 시점에 멈춰 있고, 실제 문서 포맷은 그 뒤로 두 갈래(경험 중심 lumenstate 계보, 데이터 중심 muse 계보)로 진화했다. `supabase-integration`은 muse 계보의 섹션명을 유일한 입력으로 읽으므로, 템플릿대로 쓴 문서는 다운스트림에서 바로 막힌다.
- 15세트 전수에서 반복되는 결함은 세 가지다. (1) 01에 UX 설계와 시각 디테일이 새어 들어간다. (2) 01에서 쓴 이름이 02 데이터 모델에서 다른 이름으로 바뀐다. (3) 03이 토큰 표 밖의 무드·이미지·레이아웃 정보를 매번 다른 섹션명으로 즉흥 추가한다.
- 리팩토링 방향은 "문서 3종의 골격을 하나로 통일하고, 문서 사이의 이름 계약을 명시하고, 완료도를 3단계로 표기해 100% 미완성 상태로도 다음 단계로 넘어갈 수 있게 하는 것"이다. 새 문서 종류는 추가하지 않는다.
- 실행은 세 단계(A 템플릿, B 스킬 워크플로우, C 다른 스킬과의 연결)다. 다른 스킬이 글자 그대로 찾는 섹션 제목 문구는 그대로 두므로 supabase-integration은 2줄만 고친다. 새 포맷의 실전 시험은 사용자가 직접 한다.
- 검토가 필요한 결정 8개는 9장에 모았다.

### 1.2 발견

**F1. 템플릿과 실제 계약의 드리프트.** `doc-templates.md`의 ux-flow에는 `§ 데이터 모델 활용`(이름 사전), `§ 페이지 리스트`, `§ UX-flow 단계별 서사`가 없다. `supabase-integration/SKILL.md`는 이 세 섹션과 `§ 컴포넌트 리스트`를 "유일한 입력"으로 지정하고 있다(11, 38, 120~124, 163~166행). 이 계약을 충족하는 세트는 15개 중 4개(muse, muse-test, tupac, hirst)뿐이다.

**F2. 01의 역할 붕괴.** 15세트 중 12세트에서 01-project-summary에 UX 흐름·화면 이름·컴포넌트명·색상값·모션 지시가 들어갔다. 대표 사례: oneir(샷 단위 연출 지시가 배경 문단에), tupac("Lenis 스무스 스크롤", "#C41E3A"), muse(컴포넌트명 `IntentGuideField`, "구현 완료" 상태), lumenstate(Day/Night 스크롤 전환, "카드 클릭이 아닌 시선 이동" 전환 설계). 반대로 aipark은 01의 필수 섹션(핵심 기능·대상·범위·성공 기준)을 02로 옮겨 01이 비었다. 원인은 템플릿에 "01에 쓰지 않는 것" 목록이 없고, 핵심 기능 표가 구현 디테일을 담기 쉬운 형태이기 때문이다.

**F3. 01→02 이름 단절.** 4세트에서 01의 명사가 02 데이터 모델에서 다른 이름으로 바뀌었다. mono-hand-drip("Hero"가 `Issue`로, "Visit"이 `StoreInfo`로), taste-lab(변수 4개가 카테고리 5개로), hours-of-light(제품 라인 5종이 enum 4종으로), jeju-ritual(월드뷰가 두 섹션으로 분해). 01에 이름을 처음 정의하는 자리가 없어서 02가 이름을 새로 짓는다.

**F4. 두 계보의 장단점이 상호 보완적.** lumenstate 계보는 "핵심 UX 패턴 → 유도되는 컴포넌트 유형", "상태의 영속성(정적/휘발/세션/브라우저)" 같은 경험 요구 사양이 강하지만 사전이 없고 시각 디테일이 새어 나온다. muse 계보는 사전·페이지 리스트·단계별 서사로 구현 연결이 정확하지만 인터랙션 원칙과 영속성 관점이 없다. 둘을 합치되 분량은 muse 수준으로 잡는다.

**F5. 03의 즉흥 확장.** 15세트 중 11세트(lumenstate 포함, muse·muse-test·writing-os·aipark 제외)가 토큰 표 밖의 정보(무드 키워드, 이미지·사진 룩, 레이아웃 전략, 레퍼런스 분석)를 담았는데 섹션명이 매번 다르다: "브랜드 이미지 아트디렉션"(jeju), "Reference Lock System"(oneir), "시네마틱 시퀀스 방향"(oneir), "레퍼런스 분석"(heptapod), "선이 디자인 언어다"(lumenstate). 도구형 프로젝트(writing-os, aipark, muse)는 이미지 키워드가 없어 이 자리가 비어 있다. jeju-ritual은 이미 `visual-asset-prompt`의 LOOK/FORMAT 구조로 쓰고 있어 표준화의 원형이 된다.

**F6. 문서 경계 붕괴.** 03이 구현 스펙으로 비대해지는 사례(taste-lab 261줄, SVG 좌표계·작업 분해 포함), 02가 백엔드 설계를 품는 사례(hours-of-light의 SQL 경로·RLS), 표준 3종 밖 부속 문서가 4~60개로 늘어나는 사례(heptapod, oneir, aipark). 템플릿에 "부록으로 내보내는 기준"이 없다.

**F7. 가드레일 수요가 이미 자생적으로 나타남.** 여러 세트가 템플릿에 없는 상태 관리 섹션을 스스로 추가했다: "결정 보류 항목"(hirst), "선결 결정"(writing-os), "미결정"(genre-morph), "다음 승인 게이트"(lithe, 01·02·03 모두), "자체 검증"(aipark), "총계"(mora). 이것이 사용자가 요구한 "100% 미완성 상태의 유연한 진행"의 실제 증거다.

**F8. 형식 불일치.** IA 트리 vs 페이지 리스트 표(계보별로 갈림), Mermaid 흐름도 유무(신계보는 생략), 컴포넌트 구분 컬럼(재활용/수정/신규 vs 신규만 vs 🆕/♻ 이모지 vs 사용 금지 포함), H1 구분 기호(em dash vs 마침표), 시나리오 번호 시작(0 vs 1), 구버전 파일 병존(`02-ux-flow.v1.md`).

## 2. 설계 원칙

1. **문서 3종, 파일명 유지.** `01-project-summary.md`, `02-ux-flow.md`, `03-visual-direction.md`. 다운스트림이 파일명을 참조하므로 바꾸지 않는다. 새 문서 종류를 만들지 않는다.
2. **한 골격.** 세 문서가 같은 헤더, 같은 상태 블록, 고정 번호 섹션, 같은 마지막 섹션("다음 문서로 넘기는 것")을 갖는다. 사용자는 어느 문서를 열어도 같은 자리에서 같은 종류의 정보를 본다.
3. **이름은 한 번만 짓는다.** 사용자 유형과 다루는 대상의 이름은 01에서 정하고, 02·03은 글자 단위로 그대로 쓴다. supabase-integration이 02→04 사이에 요구하는 "글자 단위 일치"를 01→02로 앞당긴다.
4. **각 문서는 자기 질문에만 답한다.** 01은 "왜, 누구를 위해, 무엇을 다루는가". 02는 "어떤 과업을 어떤 화면과 데이터로 이루는가". 03은 "어떻게 보이는가". 경계를 넘는 정보는 금지 목록으로 차단하고, 넘칠 정보는 부록으로 내보낸다.
5. **표 우선, 한 셀 한 사실.** 산문은 배경과 정체성 설명에만 허용한다. AI가 파싱할 때 해석 여지를 줄이고, 사람이 훑을 때 위치를 예측할 수 있게 한다.
6. **완료도는 3단계.** 확정 / 잠정 / 미정. 문서 상단 상태 블록에 섹션별로 표기하고, 하드 게이트(최소 완료 조건)만 넘으면 다음 문서로 진행한다. 미정 항목은 하류에서 인용하지 않는다.
7. **보편성은 슬롯의 해석으로 확보한다.** 랜딩·쇼케이스·아트·도구 어디에도 같은 섹션을 쓰되, 슬롯이 해당 없으면 "해당 없음"을 명시적으로 적는다(7장). 프로젝트 유형별 변형 템플릿은 만들지 않는다.

## 5. 워크플로우와 가드레일

### 5.1 진입 모드

스킬은 호출되면 `docs/{project}/`의 상태 블록을 먼저 읽고 현재 위치를 3줄로 보고한 뒤 모드를 고른다.

| 모드 | 조건 | 동작 |
|---|---|---|
| 신규 | docs/{project}/ 없음 | 01부터. 질문 예산 4개 |
| 이어서 | 상류 문서가 잠정 승인 이상 | 다음 문서 작성 |
| 개별 | 특정 문서만 요청 | 상류 하드 게이트 확인 후 진행. 미충족이면 무엇이 빠졌는지 표로 보여주고 멈춤 |
| 역류 | 하류 작업 중 상류 변경 필요 | 5.3 절차 |

### 5.2 완료도와 게이트

- 승인 단위는 문서다. 단, 승인은 두 종류다. **확정 승인**(모든 섹션 확정)과 **잠정 승인**(하드 게이트 충족, 나머지 잠정·미정). 잠정 승인으로도 다음 문서를 시작할 수 있다.
- 하드 게이트는 4장의 문서별 정의를 따른다. 스킬은 게이트 항목을 체크리스트로 출력하고 충족 여부를 사용자에게 보인 뒤 승인을 묻는다.
- 미정 항목은 상태 블록의 비고에 질문 번호(Q1, Q2...)를 달아 어떤 결정을 기다리는지 드러낸다.

### 5.3 잠정 진행과 역류

- **미정 의존 금지.** 하류 문서는 상류의 미정 항목을 인용하지 않는다. 필요하면 하류 작성을 멈추지 말고, 해당 셀을 미정으로 두고 상류 질문을 하나 생성한다.
- **잠정 인용 표기.** 상류의 잠정 항목을 인용한 셀에는 `(잠정)`을 붙인다. 상류가 확정되면 표기를 지운다.
- **역류 절차.** 하류 작업 중 상류를 바꿔야 하면 (1) 상류 문서의 해당 섹션을 수정하고 상태를 잠정으로 내린다 (2) 상류 상태 블록의 개정 줄을 갱신한다 (3) 하류 문서에서 영향받는 섹션을 잠정으로 내리고 비고에 "상류 n절 변경"을 적는다. supabase-integration의 "ux-flow 갱신 필요" 메시지 형식을 세 문서 사이에도 그대로 쓴다.

### 5.4 질문 예산

- 문서 하나를 시작할 때 질문은 최대 4개. 초안을 먼저 쓰고 "확인 포인트"로 묻는다(muse 기획 로그에서 검증된 패턴).
- 답이 없는 질문은 미정으로 기록하고 진행한다. 다시 묻지 않는다.

### 5.5 정합성 점검

문서를 저장하기 전 스킬이 직접 확인하는 목록. 스크립트 자동화는 이번 범위 밖이다.

| 점검 | 방법 |
|---|---|
| 01 4.2절 이름이 02 4.1절에 전부, 글자 그대로 있는가 | 이름 대조 |
| 01 5절 과업 수와 02 1절 시나리오 수가 같은가 | 개수 대조 |
| 02 3.1절 페이지가 03 2절 표에 전부 있는가 | 이름 대조 |
| 01에 금지 어휘가 없는가: hex 값, px 값, "구현 완료", 그리고 4.2절 식별자 목록에 없는 PascalCase 토큰(컴포넌트명 의심) | 정규식 + 4.2절 식별자 제외 목록 |
